## 一、现状评估

### 1.1 当前 RCA 能力基线

| 维度 | 现状 | 评价 |
| :-- | :-- | :-- |
| 规则库 | 5 条硬编码规则（`topology_dag.go` `DefaultRules`），Go 代码内置 | **最大短板**：加规则要改代码、重编译、发版 |
| 匹配方式 | 模块精确 + 助记符关键词 Contains | 覆盖率低，知识库的 `Cause`/`Impact` 字段完全未参与 |
| 算法 | 重叠窗口聚类 + 倒排索引 BFS + 实例校验 + 排他认领 + 多因子置信度 | 工程质量高，回归锚点（RCA-01~16）扎实，是**值得保留的底座** |
| 触发模式 | 导入/重分析时**全量重算**（`runRCAPipeline`），先删后插 | 无增量能力，百万级日志任务每次全扫（虽有 `maxRCALogs` 截断） |
| 分析范围 | `canCorrelate` 严格按 DeviceID/Hostname 隔离 | **与多设备协同能力割裂**：有多设备时间线，却没有跨设备 RCA |
| 置信度 | 纯规则内因子（深度/条数/时间衰减/实例） | 未利用 matcher 的 `MatchConfidence`、知识库严重度等外部信号 |
| 结果消费 | RCAEvent 持久化 + RcaGraph/RcaCenter 可视化 | 只读展示，无用户反馈闭环、无确认/否决机制 |

### 1.2 核心矛盾

1. **规则供给 vs 规则硬编码**：华为设备故障链成百上千，5 条规则只是骨架；知识库里躺着海量的 `Cause`/`Impact`/`AlarmID` 结构化数据却未被 RCA 消费。
2. **单机因果 vs 组网故障**：真实故障（如上联链路中断导致整排接入交换机邻居翻滚）天然跨设备，当前 DeviceID 隔离直接放弃了这块高价值场景。
3. **离线定位 vs 智能化诉求**：项目定位"离线、单二进制"，排除了云端 LLM 路线，但本地统计学习/轻量模型路线可行。

## 二、演进方案（三个，可组合）

### 方案 A：规则库平台化 —— 低风险、收益直接（建议先行）

把规则从代码资产变成数据资产。

- **规则外置**：`ProtocolFaultRule` 序列化为 YAML/JSON，放 `<data_dir>/rca_rules/`，启动加载 + `POST /system/rca-rules/reload` 热更新；`NewEngine(customRules...)` 已预留了注入点，改动面小。
- **规则入库与版本映射**：复用 `KnowledgeVersionMapping` 的思路，规则可按 `ProductType`/`ProductVersion` 适用（CE 交换机和 USG 防火墙的故障链不同），`matcher.FindBestKnowledgeMatch` 的版本回退逻辑可直接借鉴。
- **知识库驱动规则生成**：批量扫描知识库 `Cause`/`Impact` 字段，用关键词共现 + 模块依赖自动**草拟**候选规则（人工审核后启用），解决"规则供给"瓶颈。
- **规则生命周期**：启用/禁用开关、命中率统计（每条规则触发的 RCA 事件数）、前端规则管理页。

**工作量**：中（后端 2~3 周，前端 1 周）。**风险**：低，算法内核不动，回归测试全保留。

### 方案 B：算法增强 —— 跨设备 RCA + 信号融合（核心价值跃迁）

- **跨设备因果链**：新增设备拓扑模型（`DeviceLink{FromDevice, ToDevice, LocalIf, PeerIf}`，可手工录入或从 LLDP/接口描述参数自动推断）；`canCorrelate` 扩展为"同设备 OR 拓扑相邻且实例维度（对端 IP/接口）互证"。典型场景：SW-01 上联口 Down 与 SW-02 对应口 Down 互证，合并为一个根因，影响面跨设备展示。
- **置信度信号融合**：把 `MatchConfidence`（四级匹配的置信度）、知识条目严重度、`MatchTier` 纳入 `calculateConfidence`——Tier1 精确命中的日志作为链节点的可信度应远高于 Tier4 语义召回。
- **故障-恢复配对（会话化）**：`isRecoveryBrief` 目前只做排除；可进一步把 `DOWN`/`DOWN_CLEAR` 配对成"故障会话"，产出故障时长、是否自愈、MTTR 指标，RCA 事件增加"已恢复/持续中"状态——这是从"事后分析"走向"故障评估"的关键一步。
- **增量 RCA**：导入新日志时只对"新增日志与既有窗口边界重叠部分"做局部重算，而非全表重扫；`RCAEvent` 增加 `AnalysisVersion`/`CreatedAt` 支持幂等合并。

**工作量**：中大（跨设备拓扑 + 增量是硬骨头，4~6 周）。**风险**：中——跨设备关联是误报重灾区，需要保守策略 + 置信度降级 + 回归测试矩阵。

### 方案 C：统计学习 + 反馈闭环 —— 长期差异化

全程本地、无外部依赖，契合离线定位：

- **无规则关联挖掘**：对历史任务做频繁情节挖掘（frequent episode mining，如滑动窗口内模块-助记符共现序列），产出"统计相关但未入规则库"的候选传播链，反哺方案 A 的规则草拟。
- **用户反馈闭环**：RCA 事件增加确认/否决/改判接口（`PUT /tasks/:id/rca/:event_id/feedback`），反馈数据落库，用于：① 调整规则权重与置信度公式参数；② 否决率高的规则自动降权或停用。
- **轻量评分模型**：在积累足够反馈后，用逻辑回归/朴素贝叶斯（纯 Go 可实现，几百行）替代手工加权置信度公式，特征复用现有因子（深度/时延/实例一致性/匹配层级）。
- **可解释性增强**：RCAEvent 的传播链节点关联 `KnowledgeID`，前端 RcaCenter 展示每个节点的官方知识引用（含义/原因/处理步骤），让置信度"有据可查"。

**工作量**：大且依赖数据积累（反馈闭环先行 2 周，挖掘与模型后续迭代）。**风险**：数据冷启动——没有反馈数据时 C 方案退化，所以必须后置于 A/B。

## 三、推荐路线

```
Phase 1（近期）：方案 A 规则外置 + 知识库草拟规则 + 方案 C 的反馈闭环接口
        → 解决规则供给，开始积累标注数据
Phase 2（中期）：方案 B 信号融合 + 故障会话化 + 增量 RCA
        → 提升准确率与时效，产出"故障评估"指标（时长/自愈/MTTR）
Phase 3（远期）：方案 B 跨设备拓扑 RCA + 方案 C 统计挖掘与轻量模型
        → 形成"规则 + 统计 + 反馈"三轮驱动的差异化能力
```

**一句话结论**：现有 BFS/聚类/认领/置信度内核是合格底座，不要重写；演进重心应放在**规则数据化（A）**、**打破单机边界与信号融合（B）**、**反馈闭环与本地学习（C）**三个方向，按 A→B→C 组合推进。
