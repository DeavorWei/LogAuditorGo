# Phase 1 方案审视：主链路打通

> 审视对象：`Phase1-主链路打通-规划.md`
> 审视时间：实施前
> 审视方法：对照 §8.2 与 F1~F5/F14 逐项核对；检查与 Phase 0 已落地代码的耦合点、可测试性与回归风险

---

## 1. 总体结论

**方向成立，按 8 项调整后实施。** 最大的风险不在功能本身，而在三处“新旧并存”：**导入向导与旧导入弹窗**、**原生对话框与 Web 路径选择器**、**逐行设备归属与显式指定设备**。若不先定边界，会出现“同一任务两种导入行为”或“用户明确选了设备却被 Hostname 改写”的回归。

---

## 2. 必须调整的事项

### 2.1 原生对话框必须“可探测、可注入、可回退”

- 规划只写了端点与 COM 实现，没有定义自动化路径。Committer 无法在无桌面会话中弹窗，直接调用会阻塞或失败。
- **调整**：
  1. 增加 `GET /fs/dialog/capability`（只读，不弹窗）返回 `{supported, platform}`，前端据此决定按钮文案与回退；
  2. `internal/nativedialog` 对外暴露 `Opener` 接口 + `SetOpenerForTest`，API 层用接口注入，单元测试用假实现断言参数与错误分支；
  3. COM 失败统一返回 `ErrUnsupported`/`ErrCanceled`，API 映射为明确错误码，前端自动切换 `ServerPathPicker`；
  4. 端点叠加 `RequireLoopback`，仅本机可触发。

### 2.2 逐行归属必须尊重“显式指定设备”

- 规划写“对非主 Hostname 记录重跑 Match”，但 `ImportLogsToDevice` 的语义是“用户明确把这些日志归到某台设备”，此时按 Hostname 改归属会违背用户意图。
- **调整**：仅在 `bundle.deviceID == 0`（自动归属）时启用逐行归属；`deviceID > 0` 时保持整文件归属该设备，并在预览中标注“已指定设备，Hostname 分布仅作参考”。

### 2.3 预览与导入必须共用清洗/跳过规则

- 预览若用 `bufio.Scanner` 简单计数，会把空行、注释垃圾行、超长行算进去，导致“预览 120 行、导入 118 条”的信任问题。
- **调整**：预览复用 `logparser.IsBlankOrGarbageLine`、`SanitizeLogLine` 与 `maxScanLineBytes`；超长行在预览中直接报错（与导入一致），而不是静默计入。

### 2.4 “预计耗时”只做区间提示

- 规划用固定吞吐估算，容易被用户当成承诺。
- **调整**：返回 `estimated_seconds` 并在 UI 标注“预计（按本机历史吞吐估算）”，同时给出文件数与行数这一确定信息；不把它写进验收。

### 2.5 三个导入入口必须收口，旧弹窗降级为设备专用

- 现有 `TaskImportDialog` 被工作台、空态引导、设备管理复用。若向导只替换其中一部分，会重现“三个入口能力不一致”。
- **调整**：
  - 新建任务 / 补充导入 / 空任务引导 / Dashboard / 案例库统一走 `ImportWizard`；
  - `TaskImportDialog` 仅保留给 `DeviceManager` 的“向指定设备导入”，并在组件注释与文档中写明其边界；
  - 工作台 `importDialogRef` 改为向导实例。

### 2.6 诊断摘要必须与工作台筛选“同源”

- 摘要中的“未匹配热点”跳转如果自己拼查询，会和 `filterStore` 的语义分叉。
- **调整**：跳转只携带 `module`、`matched=false`、`log` 三个 query，工作台启动时写入 `filterStore` 后走既有 `toLogQueryBody`；不新增第二套查询参数。

### 2.7 案例结论的“草稿”不得覆盖人工结论

- 自动草稿若在每次打开抽屉时写入，会覆盖用户编辑。
- **调整**：草稿只通过显式“生成草稿”按钮插入编辑框；保存前不落库；已有 conclusion 时按钮文案为“用草稿替换”，需二次确认。

### 2.8 报告与证据包的范围控制

- 规划同时要求“报告含 RCA 摘要”与“RCA 不进主报告”，存在冲突。
- **调整**：主报告默认不渲染 RCA 章节；仅当 `features.rca=true` 且存在事件时，渲染折叠的“关联事件（实验性）”附录，并标注“非官方结论”。证据包只包含：报告 HTML、日志 CSV、元数据 JSON、说明文件；不含 RCA DAG 图片。

## 3. 补充约束

1. **只增列、不删列**：案例字段全部可空；旧库 AutoMigrate 后旧任务 `case_status=""`，UI 显示“未标注”。
2. **文件名安全**：报告/证据包文件名复用任务包内的过滤函数，去掉 Windows 非法字符与路径分隔符；长度上限 80。
3. **证据包 ZIP 流式**：直接写 `http.ResponseWriter`，禁止先 `os.CreateTemp` 再回读；CSV 复用现有流式导出函数。
4. **预览超时**：30s 上下文；超时返回已扫描部分并标记 `truncated=true`，不得 500。
5. **摘要聚合**：全部 SQL 聚合，禁止把 `[]LogRecord` 拉进内存；`first_high_log_id` 用一条 `ORDER BY severity ASC, timestamp ASC LIMIT 1`。
6. **前端向导步骤校验**：未选择来源不能进入预览；预览为空不能开始分析；创建任务失败要保留已填表单。
7. **错误态**：原生对话框失败、预览失败、导入失败分别给出可执行下一步（重试/回退/粘贴路径）。
8. **文档同步**：README 与架构说明书的导入流程、API 总表、配置说明在本阶段结束时更新。

---

## 4. 调整后的实施顺序

1. 后端基础设施：案例字段 + 迁移 → 诊断摘要 → 导入预览 → 逐行设备归属 → 原生对话框 → 报告/证据包。
2. 前端：API 封装/路由 → 导入向导（含原生对话框与回退）→ 诊断摘要页 → 结论抽屉 → 案例库字段 → 报告操作。
3. 测试：每个后端模块单测 → 端到端导入（含双 Hostname）→ 报告/证据包解压 → 前端契约脚本扩展。
4. 文档与截图，最后统一提交。

---

## 5. 审视结论

**通过（带修改）。** 按 §2 的 8 项调整与 §3 的 8 条约束实施；原生对话框以“能力探测 + 注入 + 回退”三件套保证可测与可用，逐行归属以“仅自动模式”保证不违背显式意图。
