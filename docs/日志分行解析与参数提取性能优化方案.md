## 1. 背景与现状剖析

在当前版本中，用户在导入包含数万至数百万行的日志文件，或在任务中点击"全量重新分析"时，在 **"分行解析与参数提取" (`PARSE_NORM`)** 阶段会明显感受到处理延迟高、吞吐率低。

经深入源码分析，当前并发模型与性能瓶颈现状如下：

### 1.1 并发与 Worker 线程数现状

| 运行链路 | 当前实现位置 | Worker 协程数 | 并发机制 |
| :--- | :--- | :--- | :--- |
| **首次日志导入** (`ImportLogsWithDevice`) | `internal/task/import_pipeline.go:227-285` (`parseAndMatchChunk`) | $\min(\max(\text{NumCPU}, 2), 32)$ | 协程池分批解析（在 16 核系统上为 16 个 Worker） |
| **存量重新分析** (`ReanalyzeTask`) | `internal/task/service.go:2385-2443` | **1 个（单协程）** | 单线程同步 `for` 循环逐行更新（每批 `reanalyzeBatchSize = 1000` 行，见 `reanalyze_update.go:15`） |

### 1.2 核心性能瓶颈诊断（为什么 16 线程依然慢？）

表面上看系统已在导入阶段分配了多核 Worker，但实际上性能瓶颈集中在**架构流水线断裂**与**单行重计算耦合**两个维度：

```
当前批次串行停顿架构（每 5,000 行阻塞一次）：

[ 磁盘 I/O ] ──> 读取 5,000 行
                     ↓
[ CPU 计算 ] ──> 16 个 Worker 并发解析 + 参数提取 + 知识库四级匹配 (含 Bleve 搜索)
                     ↓ (主协程 WaitGroup 阻塞等待全部完成，此时磁盘与 DB 完全闲置)
[ DB I/O  ] ──> 单协程开启 SQLite 事务执行 5,000 行落库 (此时 16 个 Worker 完全闲置)
                     ↓ (等待落库与磁盘 fsync 结束)
             下一批次循环...
```

1. **计算与 I/O 互斥等待（Stop-the-World Chunking）**：
   - 现行实现采用固定分批（`importChunkLines = 5000`）。主协程在每次分发完 5,000 行后调用 `wg.Wait()` 彻底阻塞，等待全部 Worker 执行完成后，再单线程调用 SQLite 批量插入事务。
   - **CPU 与磁盘 I/O 完全串行交替**：当数据库在执行批处理落库时，16 个 CPU 协程全部空转挂起；当 Worker 在消耗 CPU 进行正则与匹配时，数据库没有任何写入，未能形成流水线并发（Pipeline Overlapping）。
2. **"解析"与"知识库多级匹配"重耦合**：
   - 前端进度条将流程在概念上拆为了 `PARSE_NORM`（分行解析）与 `MATCH_KB`（知识库匹配），但在后端实现（`import_pipeline.go:291` `parseLogLine`）中，每一行日志在单行处理时均**同步执行了整套知识库四级匹配流水线**（`matcher/engine.go:233` `Match`）。
   - 尤其是 **Tier 4 Bleve 倒排全文检索**：若日志行在 Tier 1~3 均未命中，当前逻辑会直接同步发起 Bleve 全文搜索（`engine.go:395-463`），且搜索请求开启了 `Highlight` 与 `Fields = "*"` 全字段回填（`search/bleve_indexer.go:541-544`），开销进一步放大。在面对大量非标日志或未收录日志时，单行耗时从几微秒激增到数毫秒，极易引起 Worker 队列阻塞。
3. **文件全量"双重 I/O 扫描" (Two-Pass Scan)**：
   - 在导入前置阶段（`import_prepare.go:103` `prepareBundles`），系统为了预先计算总行数以及采样前 100 行探测 Hostname，**先从头到尾完整读取并清洗了一遍日志文件**（`scanLineSource`）；
   - 随后进入入库阶段，又通过 `persistFileBundle` **第二次从头流式重读整个文件**。
   - 【评审修订】该问题仅存在于磁盘文件路径（内存来源一次性载入只读一遍）。且预扫描只做 IO + 清洗（不含解析与匹配），在总耗时中占比有限，此瓶颈的实际权重需由阶段 0 的基线测量确认（见第 2 节）。
4. **多 Worker 并发下的全局缓存锁竞争**：
   - 【评审修订·描述修正】`pkg/cache/lru.go` 的 LRU 缓存使用单一 `sync.RWMutex`（并非 `sync.Mutex`）。但由于 `Get()` 命中后必须执行 `moveToFront` 更新 LRU 队列，**`Get` 实际走写锁**（`lru.go:46-62`），因此 16 个 Worker 并发调用 `Match` 时对 `m.cache` / `m.exactBestCache` 的读写仍会全局串行化——原判断"锁争用热点"成立，仅锁类型描述有偏差。
   - 旁证：`engine.go:573-575` 已为 `regexCache` 实现 `Peek()` 读锁快路径，注释明确承认"32 个 worker 并发匹配时所有 goroutine 串行争抢同一把锁，是实打实的热点"。本方案将把该优化思路推广到全部缓存并进一步分片化。
5. **重新分析链路完全缺乏并发**：
   - `ReanalyzeTask` 未复用 Worker 池，对数万至百万级存量日志仅采用单线程逐行扫描，吞吐量受到极大限制。这是当前**单方案收益最大、实现风险最低**的瓶颈。

## 2. 优化目标与预期指标

### 2.1 【评审修订】指标按方案归因分解

原方案将五个子方案的收益混合为"5x~10x"总目标，无法在未达标时定位归因。修订为每个子方案独立设定预期贡献与验收方法。**所有倍率均为待验证目标，前提是阶段 0 基线测量确认瓶颈归因。**

| 子方案 | 作用链路 | 预期贡献（相对基线） | 收益机理与不确定性 |
| :--- | :--- | :--- | :--- |
| 方案四：重分析并发化 | 重新分析 | **8x ~ 15x** | 单线程 → N Worker 近似线性扩展（N=16 时扣除 DB 批量更新串行占比）。确定性最高。 |
| 方案三：Tier 4 准入过滤 | 首次导入 + 重分析 | **1.2x ~ 5x（高度依赖 Tier 4 占比）** | 若基线耗时主要由未命中行走 Bleve 造成，则收益大；若 Tier 4 占比本就低，收益有限。**必须先测 Tier 4 未命中率再定目标。** |
| 方案一：三级流水线 | 首次导入 | **1.2x ~ 1.5x** | 收益上限 = DB 批量提交耗时占总耗时的比例。WAL + `synchronous=NORMAL` 下 5,000 行插入通常仅几十~几百 ms，相对解析耗时是小头。流水线的价值同时包括**消除进度停顿感**与**内存平稳**，不应只看吞吐倍率。 |
| 方案二：单遍扫描 | 首次导入 | **1.0x ~ 1.1x** | 【评审修订·收益下调】原方案估计"缩短 30%~50% 初始等待"缺乏依据：预扫描仅做 IO+清洗，SSD 上 500MB 读一遍约 1~2 秒，相对百万行解析的数分钟总耗时，占比为个位数百分比。降级为可选优化。 |
| 方案三：分片 LRU | 首次导入 + 重分析 | 并入方案三整体验收 | 锁争用占比需 profile 确认（`-mutexprofile`）。 |

**综合预期**：首次导入 2x ~ 6x（而非原方案的 5x~10x）；重新分析 8x ~ 15x。若阶段 0 测得 Tier 4 占比超过 50%，首次导入上限可上调。

### 2.2 【评审修订】新增阶段 0：基线测量与瓶颈归因（先行必做）

任何优化目标在未测量前均为假设。实施前必须完成：

1. **基准样本**：准备 10 万 / 50 万 / 100 万行真实交换机与无线 AC 日志样本，知识库使用生产规模副本；
2. **归因数据**：
   - CPU profile（`pprof`）确认 Tier 4 Bleve 搜索、正则、锁等待（`-mutexprofile`）的耗时占比；
   - 在 `Match` 中临时埋点统计 Tier 1~4 命中分布与 Tier 4 未命中率（决定方案三目标与准入规则阈值）；
   - 记录 DB 批量提交耗时占比（决定方案一收益上限）；
3. **基线吞吐**：当前导入与重分析链路各测 3 次取中位数，作为验收对照基线。

## 3. 架构优化设计（五大核心方案）

```
优化后的三级流水线架构 (Producer - Parser Workers - Ordered Committer Pipeline)：

 ┌──────────────────────────────────────────────────────────────┐
 │                      Reader (单协程流式读取)                     │
 │  - 单遍扫描：边读边分行与清洗                                     │
 │  - 【评审修订】为每个有效行分配单调递增序号 seq（文件行序唯一权威） │
 │  - 前 100 行动态嗅探 Hostname（方案二），后续持续生产             │
 └──────────────────────────────┬───────────────────────────────┘
                                │ rawLineChan: chan indexedLine{seq, text} (有界缓冲 4096)
                                ▼
 ┌──────────────────────────────────────────────────────────────┐
 │               Parse & Match Workers (N 个并发协程)             │
 │  - 分行标准化 + 参数抽取 (Fast-Path 正则与字节扫描)               │
 │  - 知识库匹配 (分片锁 LRU + Tier 4 准入过滤)                     │
 │  - 结果携带 seq 组装为 model.LogRecord                          │
 └──────────────────────────────┬───────────────────────────────┘
                                │ recordChan: chan seqRecord{seq, rec} (有界缓冲 8192)
                                ▼
 ┌──────────────────────────────────────────────────────────────┐
 │           DB Committer (单协程，【评审修订】按 seq 重排)          │
 │  - reorderBuf 缓冲乱序到达的记录，按 seq 滑窗依序释放            │
 │  - 聚合每 5,000 条或到达 FlushInterval 触发批量落库             │
 │  - 上下文时间戳平滑继承 (alignChunkTimestamps) —— 严格行序前提  │
 │  - 首个事务与 TaskFile 创建合并；失败由调用方统一补偿清理         │
 └──────────────────────────────────────────────────────────────┘
```

### 3.1 方案一：构建"读-解-写"非阻塞流式流水线 (Streaming Pipeline)

彻底打破现有的"分批等待"机制，将整个导入链路重构为三级有界缓冲流水线：

1. **Reader 协程**：
   - 负责文件转码与 `bufio.Scanner` 流式逐行扫描；
   - 负责轻量级行过滤与 `SanitizeLogLine`；
   - 【评审修订】**为每个有效行分配单调递增的 `seq`**，与行文本一起封装为 `indexedLine` 分发到 `rawLineChan`（有界缓冲区，例如 4,096）。`seq` 是文件行序的唯一权威来源；
   - 行读尽后关闭 `rawLineChan`；扫描错误（含单行超 1MB）记录后随通道关闭传播。
2. **Worker 协程池（$N = \text{NumCPU}$）**：
   - $N$ 个 Worker 从 `rawLineChan` 竞争拉取日志文本；
   - 执行 `parseLogLine`（分词、参数提取、知识库匹配；单行 panic 已由 `parseLogLine` 内部 recover 兜底，Worker 无需重复）；
   - 将 `seqRecord{seq, rec}` 写入 `recordChan`；
   - 配合 `sync.WaitGroup`，当所有 Worker 消费完毕后关闭 `recordChan`。
3. **DB Committer 协程**：
   - 单独占用一个协程专职消费 `recordChan`；
   - **【评审修订·核心】序号重排（Reorder Buffer）**：并发 Worker 的产出到达顺序是"处理完成顺序"而非文件行序——Tier 1 命中行（微秒级）与 Tier 4 慢行（毫秒级）混流时，乱序窗口可达数千行。而 `alignChunkTimestamps`（`import_pipeline.go:391-455`）的"无时间戳行继承**前序**最近有效时间戳"语义**严格依赖记录保持文件行序**，乱序会导致文件头注释行继承"未来"的时间戳、时间戳倒挂、审计排序被破坏。因此 Committer 维护 `reorderBuf map[int]model.LogRecord` 与期望序号 `nextSeq`：序号恰好轮到的记录依序进入 batch，并连带释放其后已到达的记录；乱序先行到达的暂存于 map。**在途记录总数 $\le$ `LineChanCap` + `WorkerNum` + `RecordChanCap`，缓冲天然有界**，无需额外上限保护；
   - 维护本地切片缓冲区，满足 `BatchSize`（如 5,000）或 `FlushInterval`（如 500ms，低流量尾部不被条数阈值卡住，保证进度上报及时）即触发落库；
   - **【评审修订】事务与错误边界**：
     - **首个 flush 事务与 `TaskFile` 创建合并在同一事务内**，保留现有 TASK-02/TASK-05 的原子性修复成果；
     - 任一阶段失败（读错误 / 落库错误）→ 通过 `context` 取消传播至 Reader 与 Worker → Committer **drain `recordChan` 直至关闭**，杜绝 Worker 阻塞在已无人消费的通道上造成 goroutine 泄漏（原原型在 `commitErr` 后直接 break 会让 Worker 永久挂起）；
     - 失败后已入库批次的**补偿清理统一保留在调用方 `persistFileBundle` 的 `cleanup` 路径**，本方案不改动该边界；
   - **核心收益**：当 Committer 在执行磁盘写入事务时，Worker 协程可以无缝并发解析后续的几千行日志，彻底消除 CPU 与 I/O 相互等待的停顿。

### 3.2 方案二：单遍流式处理 (Single-Pass Ingest)【评审修订：降级为可选优化】

1. **现状问题**：
   - 目前先运行一遍 `scanLineSource` 是为了准确获取 `totalLines` 从而向前端报送百分比进度、在开头提取样本嗅探 Hostname，以及**提前校验整个文件的合法性（单行超 1MB 即整文件判失败，TASK-06）**。
2. **收益重估**：
   - 预扫描只做 IO + 清洗，不含解析与匹配。SSD 上 500MB 文件预扫描约 1~2 秒，相对百万行解析的数分钟总耗时占比为个位数百分比。**该方案从"核心收益"降级为"大文件场景的可选优化"**，是否实施取决于阶段 0 测得的 IO 占比。
3. **若实施，必须补齐以下前置设计（原方案遗漏）**：
   - **嗅探缓冲与回放**：Hostname 嗅探结果决定文件名设备前缀（`[设备名]_`）、设备归集（`getOrCreateDevice`）与冲突消解（skip/overwrite/rename），这些**必须在写库前完成**。单遍模式下 Reader 需先缓冲前 100~200 行，完成嗅探与命名决策后再回放进入流水线；嗅探失败（前 100 行全注释）时沿用现有降级链（`deviceID` → 随机设备名）；
   - **`TaskFile.LineCount` 语义变更**：预扫行数不可得，改为**入库完成后按 `source_file` 聚合实际行数回写**（重分析链路已有同型实现，`service.go:2462-2479`，直接复用该模式）；
   - **进度分母**：采用"已处理字节数 / 文件总字节数"估算。需同步适配 `tr.UpdateProgress(processed, total)` 的语义与前端文案，并处理估算偏差导致的进度 >100% / 提前到 100% 的边界（钳制处理）；
   - **超长行失败时点后移**：单遍模式下 `ErrTooLong` 在流水线中途才触发，此时已落库若干批次。整文件判失败的语义不变，但清理完全依赖 `persistFileBundle` 的补偿清理路径——该路径从"理论上不会走到"变为"必须正确"，需补充针对性测试。

### 3.3 方案三：知识库四级匹配准入剪枝与分片锁优化

1. **Tier 4 Bleve 检索准入过滤 (Admission Guard)**：
   - 针对大量无法命中的冷门日志，禁止无脑调用 Bleve 全文搜索；
   - **准入条件过滤**：仅当日志具备明确的 Module（非 UNKNOWN，已有 PARSE-02 前置拦截）且 Brief 长度大于设定阈值、正文含有有效语义词时才允许进入 Tier 4；
   - **【评审修订·撤回粗粒度负缓存】**原方案提出"对未匹配的 (Module + 词根) 强化负缓存"，**予以撤回**：现有负缓存刻意按 bodyKey（含正文哈希）粒度记账，`engine.go:477` 注释明确其设计原因——"某条正文未命中，不代表同 module:brief 的另一条正文也匹配不上"。粗粒度负缓存会跳过 Tier 3 模板匹配与 Tier 4 对同类不同正文日志的召回，造成匹配率回归。且需正视：**bodyKey 粒度的负缓存对"每行正文都不同"的真实日志（含时间戳、接口号、MAC 等变量）命中率极低**——本方案真正的拦截手段是准入条件过滤，负缓存维持现状即可；
   - **误伤率评估（实施前置条件）**：准入规则可能挡掉本该 Tier 4 命中的日志，属功能回归。上线前必须用阶段 0 的基准样本做**全量回放对比**：记录"被准入规则拦截且原逻辑可命中"的行数占比，超过 0.5% 时收紧阈值或放弃该规则。
2. **LRU 缓存分片化 (Sharded LRU Cache)**：
   - 将 `m.cache` 与 `m.exactBestCache` 改造为 16 或 32 分片（Sharded LRU），Key 按哈希分散到不同锁分片；
   - 消除 `Get()` 因 `moveToFront` 走写锁导致的跨 Worker 串行化（现状见 `lru.go:46-62`）；
   - 实施次序建议：先在现有单锁 LRU 上推广 `regexCache` 已验证的 `Peek()` 读锁快路径（命中即返回、不更新 LRU 队列，允许冷数据被提前逐出——对结果缓存可接受），profile 复测后若仍有争用再上分片，避免过度工程。

### 3.4 方案四：全量重新分析 (`ReanalyzeTask`) 并发化改造

将 `ReanalyzeTask` 由当前的单线程 `for` 循环改造为**并发流式批量更新**：

1. **天然保序，直接复用现有 Worker 模式**：
   - 【评审修订】重分析与导入流水线的**关键差异**：重分析按 `id asc` 分页读取（每批 `reanalyzeBatchSize = 1000` 条），批内记录天然有主键序。并发解析时**按切片 index 就地回填**（即 `parseAndMatchChunk` 的既有模式，`import_pipeline.go:227-285`），即可完整保留 `alignChunkTimestamps` 的行序前提——**不需要方案一的序号重排机制**，改造简单且无正确性风险；
2. **并发化结构**：
   - 每批 1,000 条读入内存后，交由 Worker 池（$N = \text{NumCPU}$）并发运行 `s.parseLogLine`，按 index 回填；
   - `matchedCount` 统计改用 `atomic` 计数；
   - 维持现有 `batchUpdateLogRecords` 的 `CASE WHEN` 批量 SQL 更新机制；
3. **【评审修订】新增验证项**：并发化后写事务与后台 RCA worker 读写同一任务库的重叠压力上升，`busy_timeout=5000` + `_txlock=immediate` 配置下的 `SQLITE_BUSY` 表现需在压测中专项验证（`rca_end_to_end_test.go` 已有并发重叠场景的测试先例可扩展）。

### 3.5 方案五：SQLite 增量调优【评审修订：范围大幅收窄】

1. **现状澄清**：任务库 DSN 已在连接级配置 `journal_mode(WAL)`、`synchronous(NORMAL)`、`cache_size(-32000)`（32MB 页缓存），且已解决"连接池多连接 PRAGMA 分叉"问题（`internal/storage/task_db.go:507-522` 将全部 PRAGMA 迁入 DSN，由驱动对每条新连接逐个应用）。知识库亦然。**原方案所列"WAL 确认 + synchronous=NORMAL 注入"均为已完成的工作，不再列入实施项。**
2. **仅剩两项增量调优**（预期收益小，随阶段二顺带执行）：
   ```sql
   PRAGMA cache_size = -64000;  -- 32MB → 64MB 页面缓存（DSN 级修改）
   PRAGMA temp_store = MEMORY;  -- 批量插入排序中间结果走内存
   ```
3. **参数提取内存复用**：
   - `logparser.ExtractParametersInto(msg, params)` 接口已存在（`param_extractor.go:215`），在流水线 Worker 内复用预分配的 map 实例可减少高频 GC 分配开销。此项依赖对 `ParseLine` 内部调用链的小幅改造，归入阶段三微优化。

## 4. 关键接口与核心管道代码设计示例

### 4.1 流水线核心逻辑原型 (`internal/task/pipeline_engine.go`)

> 【评审修订】本原型相对 v1 的关键差异：**序号重排**（修复乱序破坏时间戳对齐）、**错误传播与 drain**（修复 goroutine 泄漏）、**FlushInterval 真正生效**、**TaskFile 首批同事务创建**（保留 TASK-02/05 原子性）。补偿清理保留在调用方 `persistFileBundle` 边界，本函数只负责把错误上抛。

```go
package task

import (
	"bufio"
	"context"
	"fmt"
	"io"
	"runtime"
	"sync"
	"time"

	"gorm.io/gorm"

	"logauditorgo/internal/logparser"
	"logauditorgo/internal/model"
)

// PipelineConfig 管道参数配置
type PipelineConfig struct {
	WorkerNum     int           // 并发 Worker 数 (0 => NumCPU, 夹在 [minParseWorkers, maxParseWorkers])
	LineChanCap   int           // 原始行通道容量 (如 4096)
	RecordChanCap int           // 解析结果通道容量 (如 8192)
	BatchSize     int           // 数据库批量落库条数 (如 5000, 与现有 importChunkLines 对齐)
	FlushInterval time.Duration // 强制刷盘时间窗口 (如 500ms)
}

// indexedLine 带原始行序号的日志行。
// seq 由 Reader 单调递增分配，是"文件行序"的唯一权威来源；
// Committer 依赖它把并发乱序的解析结果重排回文件行序，
// 否则 alignChunkTimestamps 的"前序时间戳继承"语义会被破坏。
type indexedLine struct {
	seq  int
	text string
}

// seqRecord 带序号的解析结果
type seqRecord struct {
	seq int
	rec model.LogRecord
}

// IngestStreamingPipeline 执行三级流式流水线导入（磁盘文件路径）。
//
// 事务与补偿边界：首个 flush 事务与 taskFile 创建合并；任一阶段失败时取消传播并
// drain 通道防止 Worker 泄漏；已入库批次的补偿清理由调用方 persistFileBundle 统一执行。
// 内存来源（bundle.lines 非空）将行切片包装为 io.Reader 后走同一管道。
func (s *Service) IngestStreamingPipeline(
	ctx context.Context,
	taskDB *gorm.DB,
	reader io.Reader,
	bundle *fileBundle,
	deviceType, deviceVersion string,
	cfg PipelineConfig,
	onProgress func(processed int),
) error {
	if cfg.WorkerNum <= 0 {
		cfg.WorkerNum = runtime.NumCPU()
		if cfg.WorkerNum < minParseWorkers {
			cfg.WorkerNum = minParseWorkers
		} else if cfg.WorkerNum > maxParseWorkers {
			cfg.WorkerNum = maxParseWorkers
		}
	}
	if cfg.LineChanCap <= 0 {
		cfg.LineChanCap = 4096
	}
	if cfg.RecordChanCap <= 0 {
		cfg.RecordChanCap = 8192
	}
	if cfg.BatchSize <= 0 {
		cfg.BatchSize = importChunkLines
	}
	if cfg.FlushInterval <= 0 {
		cfg.FlushInterval = 500 * time.Millisecond
	}

	// 派生取消信号：外部任务终止与内部任一阶段失败共用同一传播链
	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	rawLineChan := make(chan indexedLine, cfg.LineChanCap)
	recordChan := make(chan seqRecord, cfg.RecordChanCap)

	// ---- Stage 1: Reader（seq 的唯一分配者）----
	var readErr error
	go func() {
		defer close(rawLineChan)
		scanner := bufio.NewScanner(reader)
		scanBuf := make([]byte, 64*1024)
		scanner.Buffer(scanBuf, maxScanLineBytes)

		seq := 0
		for scanner.Scan() {
			text := scanner.Text()
			if logparser.IsBlankOrGarbageLine(text) {
				continue
			}
			l := logparser.SanitizeLogLine(text)
			if l == "" {
				continue
			}
			select {
			case <-ctx.Done():
				return
			case rawLineChan <- indexedLine{seq: seq, text: l}:
				seq++
			}
		}
		// readErr 写入发生在 close(rawLineChan) 之前；
		// 主流程在 recordChan 关闭并 drain 完毕后才读取，happens-before 链完整
		if err := scanner.Err(); err != nil {
			readErr = err
		}
	}()

	// ---- Stage 2: 并发 Worker 池 ----
	// parseLogLine 内部已有单行 panic recover，Worker 无需重复包裹
	var workerWg sync.WaitGroup
	workerWg.Add(cfg.WorkerNum)
	for i := 0; i < cfg.WorkerNum; i++ {
		go func() {
			defer workerWg.Done()
			for il := range rawLineChan {
				rec := s.parseLogLine(il.text, bundle.cleanName, bundle.deviceID, deviceType, deviceVersion)
				select {
				case <-ctx.Done():
					return
				case recordChan <- seqRecord{seq: il.seq, rec: rec}:
				}
			}
		}()
	}
	go func() {
		workerWg.Wait()
		close(recordChan)
	}()

	// ---- Stage 3: Committer（按 seq 重排 + 批量落库）----
	taskFile := model.TaskFile{
		TaskID:    bundle.taskID,
		FileName:  bundle.cleanName,
		FileSize:  bundle.item.FileSize,
		LineCount: bundle.totalLines,
		CreatedAt: time.Now(),
	}

	var commitErr error
	totalCommitted := 0
	first := true
	batch := make([]model.LogRecord, 0, cfg.BatchSize)
	lastFile := bundle.cleanName
	var lastValidTS time.Time

	// reorderBuf 暂存"已到达但序号尚未轮到"的记录。
	// 在途记录总数 <= LineChanCap + WorkerNum + RecordChanCap，缓冲天然有界。
	reorderBuf := make(map[int]model.LogRecord, cfg.RecordChanCap)
	nextSeq := 0

	flush := func() error {
		if len(batch) == 0 && !first {
			return nil
		}
		alignChunkTimestamps(batch, &lastFile, &lastValidTS)
		err := taskDB.Transaction(func(tx *gorm.DB) error {
			if first {
				if err := tx.Create(&taskFile).Error; err != nil {
					return fmt.Errorf("create task file record failed: %w", err)
				}
			}
			if len(batch) > 0 {
				if err := tx.CreateInBatches(batch, 1000).Error; err != nil {
					return fmt.Errorf("batch insert log records failed: %w", err)
				}
			}
			return nil
		})
		if err != nil {
			return err
		}
		totalCommitted += len(batch)
		first = false
		if onProgress != nil {
			onProgress(totalCommitted)
		}
		batch = batch[:0]
		return nil
	}

	// deliver 把"序号恰好轮到"的记录依序送入 batch，并连带释放其后已到达的记录
	deliver := func(rec seqRecord) {
		if rec.seq != nextSeq {
			reorderBuf[rec.seq] = rec.rec
			return
		}
		batch = append(batch, rec.rec)
		nextSeq++
		for {
			pending, ok := reorderBuf[nextSeq]
			if !ok {
				break
			}
			delete(reorderBuf, nextSeq)
			batch = append(batch, pending)
			nextSeq++
		}
	}

	ticker := time.NewTicker(cfg.FlushInterval)
	defer ticker.Stop()

consumeLoop:
	for {
		select {
		case rec, ok := <-recordChan:
			if !ok {
				break consumeLoop // 正常 EOF：recordChan 已关闭
			}
			deliver(rec)
			if len(batch) >= cfg.BatchSize {
				if err := flush(); err != nil {
					commitErr = err
					break consumeLoop
				}
			}
		case <-ticker.C:
			if err := flush(); err != nil {
				commitErr = err
				break consumeLoop
			}
		}
	}

	if commitErr != nil {
		// 失败路径：取消 Reader/Worker，并 drain recordChan 直至关闭，
		// 杜绝 Worker 阻塞在已无人消费的通道上（goroutine 泄漏）
		cancel()
		for range recordChan {
		}
		return commitErr
	}

	// 正常 EOF：全部 seq 已交付，reorderBuf 必为空，做防御性校验
	if len(reorderBuf) > 0 {
		return fmt.Errorf("pipeline integrity violated: %d records stuck in reorder buffer", len(reorderBuf))
	}
	if len(batch) > 0 || first {
		if err := flush(); err != nil {
			return err
		}
	}
	// 读错误（含单行超 1MB，TASK-06 语义）最后上抛；
	// 已提交批次由调用方 persistFileBundle 的 cleanup 补偿清理
	return readErr
}
```
