# 高级筛选与标签系统设计方案（最终版）

> 状态：已评审定稿。本方案在前版基础上吸收了 5 项安全隐患审计结论（REGEXP 回调 panic、
> 覆盖导入孤儿标签、标签筛选 JOIN 行膨胀、回填索引前缀缺失、前端组件膨胀），
> 并完成了全部关键技术前提的 PoC 实测验证（见第三节）。
> 关联文档：`docs/架构与模块说明书.md`（5.14 任务库 / 7.2 查询链路）、`docs/RCA演进计划.md`。

## 一、背景与目标

工作台当前筛选链路为三层扁平结构：前端 `web/src/stores/filter.js`（扁平字段 + localStorage 持久化）
→ `internal/api/task_handler.go` `QueryLogs`（逐个手写解析 query 参数）
→ `internal/task/service.go` `applyKeywordFilter`（单值多字段 LIKE）。

存在四个根本短板：

1. **扩展模型僵硬**：每加一个筛选维度要动四层（控件 → store → handler → service SQL），撑不住"丰富筛选规则"的诉求；
2. **表达能力天花板低**：无 OR / NOT / 多值 / 正则 / 组合逻辑；
3. **参数不可筛**：解析器抽取的 `parameters_json`（PeerIP、接口名等最有审计价值的字段）完全无法参与筛选；
4. **无圈选与标注能力**：审计工作流缺"圈选 → 命名 → 复检"的闭环。

目标：左栏日志列表右上角新增**高级筛选**入口（多条件构造 + 正则 + 参数筛选 + 命中预览），
配套**标签系统**（按筛选结果批量打标 / 单条打标 / 按标签快速检索），并让导出与圈选子集一致。

## 二、关键架构决策

| 决策 | 结论 | 理由 |
| :-- | :-- | :-- |
| 标签数据位置 | **任务库**（非全局库） | 遵守"任务级物理隔离、自包含、删除无残留"原则；重分析已验证为按 ID 游标 UPDATE（`service.go:2064`），日志 ID 稳定，标签关联在重分析后依然有效 |
| 查询与打标共用条件编译 | 统一 `buildLogFilterScope()` | 从代码结构上排除"看到的 N 条 ≠ 标到的 M 条"——本功能最大的可信度风险 |
| API 形态 | 新增 `POST /tasks/:id/logs/query` 统一查询入口 | 条件组为嵌套结构，URL query 装不下；旧 `GET /logs` 仅作兼容保留，前端统一切新端点 |
| 正则实现 | **SQL 层 REGEXP 自定义函数**（Go RE2 + 编译缓存 + NULL 防御） | PoC 实测可行（见 3.1）；RE2 线性时间引擎天然免疫 ReDoS |
| 参数筛选 | **`json_extract` + `json_valid` 防御包装** | 裸 `json_extract` 在空串 JSON 行上必然整体失败（PoC 实测，见 3.2），必须防御 |
| 孤儿标签防治 | **外键级联删除（主）+ 一次性自愈清理（辅）** | 任务库 DSN 已开启 `_pragma=foreign_keys(1)`（`task_db.go:422`，已核实），级联天然覆盖所有删除路径 |
| 条件逻辑复杂度 | 第一版只做**顶层扁平 AND/OR** + 单条件 NOT | 嵌套分组 Query Builder 是 UI 巨兽；OR 覆盖绝大多数组合场景 |
| 前端组件 | **独立组件拆分**（`AdvancedFilterDrawer.vue` / `TagManagerModal.vue`） | `AuditWorkbench.vue` 已约 2,600 行 / 84KB，禁止继续膨胀 |

## 三、关键技术验证（PoC 实测结论）

以下结论来自在项目依赖环境（`github.com/glebarez/go-sqlite` v1.21.2 + `modernc.org/sqlite` 内核）
下运行的真实测试，非推断：

### 3.1 REGEXP 自定义函数

- `RegisterDeterministicScalarFunction("REGEXP", 2, ...)` 注册后可在 GORM `Where("col REGEXP ?", pat)` 中直接使用；
- **NULL 形态实测**：SQL NULL 列传入回调时 `args[i]` 为 `nil`（非 `""`），直接 `.(string)` 断言必 panic，
  且 panic 沿纯 Go 转译栈传播、驱动层无 recover → **进程崩溃**。防御式写法（见 5.4）实测通过；
- 坏正则（如 `[invalid`）返回 SQL 错误 `error parsing regexp: ...`，不崩溃——但必须在 handler 层前置编译校验，
  给用户行级错误提示，而非让 500 抛到底；
- `COALESCE(col,'') NOT REGEXP ?` 写法实测能保留 NULL 行（三值逻辑防御有效）。

### 3.2 json_extract 参数筛选

- `json_extract(parameters_json, '$.PeerIP')` 在 **`parameters_json` 为空字符串的行上使整条查询报
  `SQL logic error: malformed JSON`**。`LogRecord.ParametersJSON` 对未解析出参数的日志即为空串，
  因此裸写法在线上**必然触发**。这是对审计建议的关键修正点；
- 防御写法 `CASE WHEN json_valid(parameters_json) THEN json_extract(...) ELSE NULL END` 实测通过：
  空串/NULL 归一为 NULL（不命中、不报错），kv LIKE 与 kv REGEXP 均正常工作。

### 3.3 REGEXP 性能基准（20 万行，内存库，go test 环境）

| 场景 | 耗时 | 说明 |
| :-- | :-- | :-- |
| 单正则全表扫描 | **1.42s**（~7μs/行） | 最坏情形；外推百万行约 7s，在 RCA 5 分钟超时预算内但体感慢 |
| 前置可索引条件缩小候选后（2 万行） | **129ms** | 叠加时间/设备/级别/ID 条件后性能线性可控 |
| 双正则组合（REGEXP + NOT REGEXP/COALESCE） | **1.61s** | 多条件叠加代价可控 |

结论：可行，但 UI 必须引导"先用可索引条件缩小范围，再上正则"（Drawer 内置提示 + 命中预览实时反馈）。

### 3.4 外键级联前提

任务库连接 DSN（`storage/task_db.go:417-425`）已含 `&_pragma=foreign_keys(1)`，
GORM `constraint:OnDelete:CASCADE` 生成的 FK DDL 会被 SQLite 实际执行。已核实覆盖两条 LogRecord 物理删除路径：
覆盖导入清理（`import_prepare.go:209`）与失败补偿清理（`import_pipeline.go:420`）。

### 5.1 数据契约

```go
// internal/model/advanced_filter.go —— 前后端共用 JSON 契约
type AdvancedCondition struct {
```

统一查询请求体（`POST /api/v1/tasks/:id/logs/query`，同时服务查询、命中预览、批量打标、导出）：

```json

  "page": 1, "page_size": 50, "after_id": 0, "sort_by": "time", "order": "asc",
  "keyword": "BFD", "severity": 4, "matched": true, "device_id": 2,
  "module": "", "time_start": null, "time_end": null,
  "advanced": {
    "logic": "AND",
    "conditions": [
      { "field": "raw_log",     "op": "regex",       "value": "BFD_SESS_DOWN|IF_DOWN" },
      { "field": "parameters",  "op": "kv_contains", "value": "PeerIP=10.1.1." },
      { "field": "module",      "op": "not_in",      "value": "DEVM,COMMENT" },
      { "field": "match_tier",  "op": "in",          "value": "EXACT,MNEMONIC" },
```

约束：`conditions ≤ 10`，单 `value ≤ 256 字节`，regex 值在 handler 层前置 `regexp.Compile` 校验
（失败返回 400 + 行号与编译错误，Drawer 内联展示）。

### 5.2 字段与操作符白名单矩阵（防注入核心）

| 字段键 | 实际列 | 类型 | 支持的操作符 |
| :-- | :-- | :-- | :-- |
| `raw_log` | raw_log | 文本 | contains / not_contains / regex / not_regex / eq / prefix / suffix |
| `message_body` | message_body | 文本 | 同上 |
| `brief` | brief | 文本 | 同上 + in / not_in |
| `module` | module | 文本 | 同上 + in / not_in（不区分大小写） |
| `hostname` | hostname | 文本 | contains / not_contains / regex / not_regex / eq / prefix / suffix |
| `slot_info` | slot_info | 文本 | contains / not_contains / regex / not_regex / eq / prefix / suffix |
| `source_file` | source_file | 文本 | eq / contains / prefix |
| `parameters` | parameters_json | KV JSON | kv_contains / kv_not_contains / kv_eq / kv_regex / kv_not_regex（见 5.5） |
| `severity` | severity | 数值 | lte / gte / lt / gt / eq / in |
| `match_tier` | match_tier | 枚举 | eq / in / not_in |
| `match_confidence` | match_confidence | 数值 | gte / lte / gt / lt / eq |
| `knowledge_id` | knowledge_id | 数值 | gte / lte / gt / lt / eq |

编译器表驱动：`field → 列名`、`op → SQL 片段模板` 两份白名单硬编码于 `internal/task/advanced_filter.go`。
**值永远走参数绑定；操作符与列名永远不出现在拼接字符串里**；白名单外的 field/op 直接 400。

### 5.3 条件编译器规则

- 顶层 `Logic="AND"`：逐条 `query.Where(...)`；
- 顶层 `Logic="OR"`：同层条件包成一个括号组 `(c1 OR c2 OR c3)`（`gorm.Expr` / 字符串拼接括号 + 绑定参数）；
- **NOT 类操作符的三值逻辑防御**（SQLite 中 `NULL NOT LIKE 'x'` 为 NULL，会被 WHERE 静默丢弃）：
  所有 not_* 一律编译为 `COALESCE(col, '') NOT LIKE ?` / `COALESCE(col, '') NOT REGEXP ?`，
  保证"字段为空的行不被静默排除"（PoC 实测通过）；
- `in` / `not_in`：value 按逗号切分为切片后走 `IN (?)` 绑定；空集语义明确化（`not_in` 空集 = 恒真跳过）；
- **标签过滤必须用子查询，禁止 JOIN**（防行膨胀破坏 COUNT 与分页）：

```sql
-- tag_logic = "any"
id IN (SELECT log_id FROM log_tag_relations WHERE tag_id IN (?))
-- tag_logic = "all"
id IN (SELECT log_id FROM log_tag_relations WHERE tag_id IN (?)
       GROUP BY log_id HAVING COUNT(DISTINCT tag_id) = ?)
```

- 编译产物为 `(sqlFragment, args)` 二元组，由查询 / 打标 / 摘标 / 导出四个入口**共用同一实现**；
- `advanced` 为空对象时行为与现有查询完全一致（回归基线）。

### 5.4 REGEXP 安全实现（`internal/storage/sqlite_funcs.go`）

```go
import gosqlite "github.com/glebarez/go-sqlite"

// 进程级注册一次（sync.Once）。确定性注册允许 SQLite 做常量折叠优化。
var registerOnce sync.Once

func RegisterSQLiteFunctions() {
    registerOnce.Do(func() {
        _ = gosqlite.RegisterDeterministicScalarFunction("REGEXP", 2,
            func(ctx *gosqlite.FunctionContext, args []driver.Value) (driver.Value, error) {
                // [审计修正 #1] NULL 防御：SQL NULL 以 nil 形态传入回调，
                // 直接类型断言会 panic 且沿转译栈传播导致进程崩溃。
                // NULL 不匹配正则，符合三值逻辑。
                if len(args) < 2 || args[0] == nil || args[1] == nil {
                    return false, nil
                }
                pat, ok1 := args[0].(string)
                val, ok2 := args[1].(string)
                if !ok1 || !ok2 {
                    return false, nil
                }
                re, err := reCache.GetOrCompile(pat)
                if err != nil {
                    return nil, err // 坏模式 → SQL 错误，不崩溃（handler 层已前置校验，此处为兜底）
                }
                return re.MatchString(val), nil
            })
    })
}
```

编译缓存（`reCache`）：`RWMutex` 保护的 `map[string]*regexp.Regexp`，双检锁模式，
容量上限 256、满则整体清空（简单有界策略，避免动态正则耗尽内存）。
注册时机：`main.go` 服务启动时（在 `storage.InitKnowledgeDB` 之前），全局一次。

### 5.5 parameters 参数筛选（JSON 路径安全）

**两道防御是本节的核心，缺一不可（均有 PoC 实测依据）：**

1. **json_valid 包装**（防 malformed JSON 整体失败）：

```go
// value 形如 "PeerIP=10.1.1."，解析为 key="PeerIP"、val="10.1.1."
// key 必须先过白名单校验（见下），再进入 SQL
const kvExpr = "CASE WHEN json_valid(parameters_json) " +
    "THEN json_extract(parameters_json, '$.' || ?) ELSE NULL END"

case "kv_contains":     // → kvExpr + " LIKE ? ESCAPE '\\'"，绑定 key, "%"+escapeLike(val)+"%"
case "kv_not_contains": // → "COALESCE(" + kvExpr + ", '') NOT LIKE ? ESCAPE '\\'"
case "kv_eq":           // → kvExpr + " = ?"
case "kv_regex":        // → kvExpr + " REGEXP ?"（val 已过前置编译校验）
case "kv_not_regex":    // → "COALESCE(" + kvExpr + ", '') NOT REGEXP ?"
```

2. **key 白名单校验**（防 JSON path 注入）：`'$. ' || ?` 是字符串拼接，key 来自用户输入，
   必须匹配 `^[A-Za-z0-9_][A-Za-z0-9_\-.]{0,63}$` 方可进入 SQL，否则 400。
   值中的 `"` `\` `%` `_` 由 escapeLike 处理。

### 5.6 标签系统数据模型与孤儿防治

```go
// internal/model/tag.go —— 注册进 task_db.go AutoMigrate 列表
type LogTag struct {
    ID        uint      `gorm:"primaryKey;autoIncrement" json:"id"`
    Name      string    `gorm:"size:64;uniqueIndex" json:"name"`
    Color     string    `gorm:"size:16" json:"color"`  // 预设色板
    Remark    string    `gorm:"size:255" json:"remark"`
    CreatedAt time.Time `json:"created_at"`
}

type LogTagRelation struct {
    ID        uint      `gorm:"primaryKey;autoIncrement"`
    TagID     uint      `gorm:"uniqueIndex:uniq_tag_log,priority:1"` // (tag_id, log_id) 复合唯一：防重 + INSERT 冲突吞并 + 服务 tag_id 前导查询
    LogID     uint      `gorm:"uniqueIndex:uniq_tag_log,priority:2;index:idx_tag_rel_log_id"` // [审计修正 #4] 独立 log_id 索引：服务回填 WHERE log_id IN (50)
    CreatedAt time.Time
    // [审计修正 #2] 外键级联：LogRecord 被物理删除（覆盖导入/补偿清理）时自动清理关联，
    // 覆盖所有删除路径。前提已核实：任务库 DSN 已开启 foreign_keys(1)。
    LogIDFK   uint      `gorm:"column:log_id;constraint:OnDelete:CASCADE"` // 实际以 GORM FK tag 形式落在 LogID 字段上
}
func (LogTagRelation) TableName() string { return "log_tag_relations" }
```

> 注：实际实现中 FK 约束直接声明在 `LogID` 字段上（`gorm:"index:idx_tag_rel_log_id;constraint:OnDelete:CASCADE"`），
> 上方拆成两行仅为注释清晰。**双保险自愈**：`GetOrCreateTaskDB` 迁移后执行一次
> `DELETE FROM log_tag_relations WHERE log_id NOT IN (SELECT id FROM log_records)`，
> 兜住历史残留与任何未预期的删除路径（幂等，代价可忽略）。

批量打标与查询共用条件编译（杜绝"看到的 ≠ 标到的"）：

```go
// 同一 buildLogFilterScope(taskDB, queryBody) 产出 scope *gorm.DB（未 Finalize）
// 查询入口：  scope.Count() / scope.Order(...).Limit(...).Find(...)
// 批量打标：  taskDB.Exec("INSERT OR IGNORE INTO log_tag_relations (tag_id, log_id) SELECT ?, id FROM (?)", tagID, scope)
// 批量摘标：  taskDB.Exec("DELETE FROM log_tag_relations WHERE tag_id = ? AND log_id IN (SELECT id FROM (?))", ...)
```

分页回填：查出当页 50 条后 `WHERE log_id IN (…)` 走 `idx_tag_rel_log_id` 二次查关联表组装 `tags` 字段
（避免 JOIN 行膨胀破坏分页）。

其他工程约束：

- 单次批量打标上限 50 万行（前端超限二次确认）；> 5 万行走现有 `progress.JobTracker` 异步 job + SSE（复用 `ImportProgressModal`）；
- 打标只写 `log_tag_relations`，与导入/重分析无数据冲突，不抢 `getTaskLock`（避免把导入任务卡死）；SQLite WAL 单写者天然串行化；
- 删除任务 = 物理删库文件，标签随库消失，零残留，符合隔离模型。

  沿用现有 deep watch 持久化机制；`activeFilterCount()` 把高级条件数与标签数计入徽标；

## 六、审计隐患修正对照表

| # | 隐患 | 验证结论 | 最终方案落点 |
| :-- | :-- | :-- | :-- |
| 1 | REGEXP 回调 nil/断言 panic（高危） | **实测证实**：NULL 以 nil 传入回调，断言 panic 沿纯 Go 转译栈传播，驱动无 recover → 进程崩溃 | 5.4 防御式回调（len/nil/双重断言三重防御），PoC 通过 |
| 2 | 覆盖导入孤儿标签（高危） | **实测证实**：`import_prepare.go:209` 与 `import_pipeline.go:420` 两条物理删除路径均存在；另发现 DSN 已开 `foreign_keys(1)` | 5.6 FK 级联（主，天然覆盖全部删除路径）+ 迁移后一次性自愈清理（辅） |
| 3 | 标签筛选 JOIN 行膨胀（中危） | 分析成立 | 5.3 强制 IN 子查询（any / GROUP BY HAVING all），测试锚点 ADV-07 |
| 4 | 回填查询缺 log_id 前导索引（中危） | 分析成立：复合唯一索引 (tag_id,log_id) 不服务 log_id 前导 | 5.6 `LogID` 独立索引 `idx_tag_rel_log_id` |
| 5 | AuditWorkbench.vue 组件膨胀（中危） | 成立（约 2,600 行 / 84KB） | 5.8 两个独立组件 + 独立 tag store |

对审计"优化建议"的修正采纳说明：

- **json_extract 升级**：方向采纳，但审计原样存在两个被 PoC 证实的缺陷——
  ① 裸 `json_extract` 在空串 JSON 行上使整条查询失败（`malformed JSON`），而 `parameters_json` 大量为空串，
  必须以 `json_valid` 包装（5.5 防御 1）；② `'$. ' || ?` 的 key 拼接存在 JSON path 注入，key 必须过
  `^[A-Za-z0-9_][A-Za-z0-9_\-.]{0,63}$` 白名单（5.5 防御 2）；
- **导出协同**：采纳，`POST /tasks/:id/export` 复用同一查询体（5.7）；
- **正则编译缓存**：采纳（双检锁 + 256 上限满则清空），实现在 5.4；
- **组件拆分**：采纳并扩展为三件套（Drawer / Modal / tag store）。

## 七、风险与对策

| 风险 | 等级 | 对策 |
